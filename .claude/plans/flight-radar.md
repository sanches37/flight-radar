## P-1a — fast-flights 통합권 연결  ✅ 완료

실측으로 확정된 것 (2026-08-21, fast-flights 3.1.0):

- `curr=KRW`로 **가격이 KRW 정수**로 온다. 통화 필드 불필요 → 트리거 대기 항목 유지

- `metadata.airlines`가 이름→IATA 매핑을 준다 → `carriers`는 코드로 저장
- 요청당 ~1.3초. 3초 간격 삽입 시 30요청 = 실행당 ~2분 10초. 차단 없었음
- 수집량: 실행당 222건 (date pair 30 × 여정 5~11)

**함정 2개 (재발 방지용으로 테스트에 고정)**

1. **duration을 현지시각 뺄셈으로 구하면 안 된다.** 출·도착 시각은 각 공항 현지시각이라
   ICN→LIS에서 8시간이 조용히 사라진다 (29h15m → 21h15m). 구간 duration 합 + 경유 대기
   (같은 공항이므로 뺄셈 안전)로 계산한다. `google_flights.py:_elapsed_minutes`
2. **fast-flights 3.1.0 파서 버그.** `parser.py:77`이 가격을 무조건 읽어서, Google이
   "가격 미제공"으로 주는 여정(`k[1] == [[], "..."]`)이 하나라도 섞이면 `IndexError`로
   **그 페이지 전체가 날아간다.** 실측에서 icn-lis 15쌍 중 8쌍 손실.
   `_parse`가 파싱 전에 해당 항목을 걸러낸다. upstream이 고치면 이 8줄을 지우고
   `get_flights`로 되돌리면 된다

**종료 후 리뷰**: 발견 2건 → 수용 2 / 기각 0 / 트리거 대기 0.
(`pause_seconds` 생성자 파라미터 = 호출처 0곳 YAGNI → 상수로 환원 /

## P-1c — 파서 누락 수정  ✅ 완료

**fast-flights가 Google의 "Best departing flights" 섹션을 통째로 안 읽는다.**
SerpApi 병행 실험(2026-08-21)에서 발견:

```
payload[2][0]  Best departing flights   3개   ← 아무도 안 읽는다
payload[3][0]  Other departing flights  8개   ← _parse가 읽는 유일한 곳
```

같은 시각 같은 쿼리(ICN↔LIS 10/06~10/15) 비교:

| | fast-flights | SerpApi | 차이 |
|---|---|---|---|
| 여정 수 | 7 | 10 (+가격없음 1) | **3개 누락** |
| 제약 만족 최저가 | 1,388,300 | **1,156,200** | **-232,100원** |

누락된 3개가 전부 **가장 싼 것들**이다. 지금까지 쌓인 히스토리 전부가
Google이 최상단에 올리는 운임을 빠뜨린 채 수집됐다. 알림 판정도 그만큼 둔했다.

**수정 완료**: `_itineraries()`가 두 섹션을 합치고 `_parse`가 가격 없는 항목만
걷어낸다. **dedupe는 넣지 않았다** — 두 섹션의 가격 집합이 실측에서 서로소였고
(best {1120100, 1156200, 1419800} / other {1388300, ...}), Google이 애초에
목록을 나눠 주기 때문. 겹치는 사례가 관측되면 그때 넣는다.

**실측 검증**: 수정 후 같은 쿼리에서 여정 10개 — SerpApi 유효 10개와 목록·가격
전부 일치. 제약 만족 최저가 1,388,300 → **1,156,200원**.

**남는 부작용**: 어제까지 쌓인 히스토리는 best 섹션이 빠져 있어 baseline이
인위적으로 높다. `_recent_low`가 그 위에서 최저를 잡으므로 앞으로 30일간
drop 알림이 실제보다 쉽게 뜬다. 데이터가 밀려나가면 자연 해소되므로 방치.

**부수 검증 (같은 실험에서 확인된 것)**

- `_elapsed_minutes`가 SerpApi `total_duration`과 **7/7 일치**. 현지시각 뺄셈
  함정 우회가 정확하다는 독립 확인
- "가격 미제공" 여정은 SerpApi 응답에도 있다 (ICN>PEK>LHR>LIS). 우리 우회가 타당

## P-1b — 분리 발권 조합

**P-2 뒤로 미뤘던 이유** (이제 해소): P-4 percentile 판정이 30일 히스토리를 요구하는데
출발까지 45일뿐이었다. 통합권만이라도 매일 쌓기 시작하는 것이 급했다.

1. `인천→허브`와 `허브→목적지`를 따로 조회해 합산 (`Quote.legs` 채움)
2. 자가환승 최소 연결시간 가드 (예: 3시간 미만 조합 제외)
3. **요청량 압축이 핵심.** 순진하게 짜면 실행당 130+요청(≈9분).
   - ICN→허브 / 허브→ICN은 **두 노선(LIS·OPO)이 공유**한다 → 허브당 11요청, 4허브 = 44
   - 목적지 구간은 허브×목적지당 11요청 = 88
   - 실측 출발일 5개 / 귀국일 5개뿐이므로 date pair가 아니라 **날짜 단위로 캐시**하면
     같은 실행 안에서 재사용된다. 이 캐시를 provider에 둘지 tracker에 둘지 P-1b에서 결정
4. 허브 4개가 과한지 실측 후 축소 검토

**오픈조(리스본 in / 포르투 out)는 여기에 얹힌다** — 실측 2026-08-21:

- **통합권 다구간은 이 방식으로 불가.** fast-flights가 `multi-city` 쿼리는 만들지만
  Google이 결과를 서버 렌더링하지 않는다. 같은 날짜로 비교하면 왕복은 `ds:1`이
  66,067자(여정 포함), 다구간은 5,579자(공항 이름·좌표뿐). JS 실행 후 XHR로 결과가
  오는 구조라 HTML 파싱으로는 닿지 않는다. 브라우저 자동화를 붙이면 되지만
  "provider 파일 하나만 갈아끼운다"는 전제가 깨지므로 하지 않는다
- **장거리 편도 합산은 오픈조의 상한선일 뿐 — 오픈조 추정치로 쓰면 안 된다.**
  ICN→LIS 편도 914,200 + OPO→ICN 편도 1,468,385 = 2,382,585원이었지만,
  진짜 오픈조 운임은 그 절반 수준이었다 (아래 표). 편도는 편도 운임 체계로,
  오픈조는 왕복 운임 체계로 매겨지기 때문
- **~~유럽 내 구간은 편도 페널티가 거의 없다~~ — 틀렸다.** 처음 잰 CDG→LIS 210,304 /
  OPO→CDG 129,834는 **제약 필터를 안 건 최저가**라 MAD 경유 10시간, BEG 경유 7시간
  같은 아무도 안 탈 라우팅이었다. 직항 기준으로 다시 재면 CDG→LIS 413,732,
  MAD→CDG 191,401 — 두 배 이상이다. 유럽 내 구간에도 제약 필터가 필수

**마드리드 비교 실측 (2026-08-21, 10/06 출발 · 10/15 귀국 1회 스냅샷)**

| | 값 | 비고 |
|---|---|---|
| MAD→ICN 편도 | 1,044,774 | OPO→ICN 1,468,385보다 42만 싸다 |
| ICN↔MAD 왕복 통합권 | 1,888,500 | LIS 왕복보다 50만 비싸다 |
| ~~오픈조 편도합산 LIS in/MAD out~~ | ~~1,958,974~~ | **무효 — 상한선일 뿐** |
| 분리발권 오픈조 (CDG 경유) | 2,039,133 | 왕복 대비 +88만 |
| **ICN↔LIS 왕복 통합권** | **1,156,200** | SerpApi 기준 진짜 최저 |

**진짜 오픈조 운임** (SerpApi `type=3` multi_city_json, 제약 경유≤1·23h 적용):

| 조합 | 값 | 왕복(1,156,200) 대비 |
|---|---:|---:|
| LIS in / **MAD** out | **1,273,800** | **+117,600** |
| LIS in / OPO out | 1,383,200 | +227,000 |

**→ 오픈조는 실용적인 선택지다.** 앞서 "왕복 대비 +57~65만"이라 적은 것은
편도 합산으로 추정한 탓이며 **틀렸다.** 마드리드로 나오는 데 실제로 드는
추가 비용은 12만원 수준이고, 리스본→마드리드 육로 이동을 일정에 넣고 싶다면
충분히 지불할 만하다.

**→ P-1b 전제를 다시 봐야 한다.** 이 날짜에는 `ICN↔CDG 왕복 1,434,000`이
`ICN↔LIS 왕복 통합권 1,388,300`보다 **비싸다**. 허브까지 가는 값이 목적지까지 가는
값보다 비싸면 분리 발권은 원리상 못 이긴다. 가장 싼 허브 왕복(DOH 1,083,800)에
유럽 구간을 얹어도 통합권을 못 넘긴다.

**단, 1개 날짜 조합의 1회 스냅샷이다.** P-1b 착수 전 서로 다른 날짜 3~4개로
"허브 왕복 < 목적지 왕복"이 성립하는 구간이 있는지부터 확인할 것.
성립 안 하면 P-1b는 남은 45일 동안 가치가 낮고, P-3(대시보드)·P-4(percentile)가
먼저다 — 지금 데이터가 말하는 건 "리스본 통합권 왕복을 언제 살까"이므로.

**다음 Step에서 깨질 것**: 요청량이 3배가 되면 P-2의 Actions 실행 시간·차단 위험도 3배.

## P-2 — GitHub Actions cron  ✅ 완료

`.github/workflows/track.yml` — 07:05 / 19:05 KST (`5 22`/`5 10` UTC),
`workflow_dispatch` 포함. `data/`·`state/` 자동 커밋 `[skip ci]`.

**세 가지를 했다**

1. **알림 상태 오염 수정.** `suppress_repeats`를 거르기 전용으로 만들고
   `record_sent`를 새로 뒀다. `cli.deliver()`가 **발송 → 기록** 순서로 부른다.
   `--dry-run`은 `deliver()` 앞에서 return하므로 알림 상태를 일절 건드리지 않는다.
   실측으로 확인: fake 한 사이클에서 알림 2건이 발사됐고, 고치기 전이라면
   dry-run 한 번이 그 2건을 7일간 막았을 상황이었다
2. **조용한 죽음 감시** (`health.py`). `state/health.json`에 연속 0건 횟수를 쌓고
   3회(≈1.5일) 이상이면 텔레그램 경고. **임계 도달 이후 매 실행 반복 발송**한다 —
   crossing 1회만 쏘면 그 한 번이 전송 실패로 날아갈 때 감시가 통째로 무력해진다
3. **커밋 스텝은 `if: always()`.** 중간에 죽어도 이미 디스크에 쓴 실제 가격은
   버리지 않는다. 히스토리에 구멍을 남기는 쪽이 더 나쁘다

**첫 실행 검증 완료** (run `32439725494`, 커밋 `a7adf10`)

```
10/05..10/16  무제약 1,660,300  제약 1,948,700  (+17.4%)
10/09..10/16  무제약 1,748,300  제약 1,948,700  (+11.5%)
10/06..10/15  무제약 1,120,100  제약 1,156,200  ( +3.2%)
나머지 9쌍     차이 0
```

### 실측 3 — 날짜쌍 하나만 보면 틀린 매수 신호가 나간다 (구현 중 발견)

처음 설계는 "노선 최저가 견적의 **그 날짜쌍** percentile"이었다. 전 규모 실행에서
바로 깨졌다:

```
icn-lis 최저가 1,156,200원 (10/06..10/15) → 그 쌍의 percentile 75%
같은 가격의 10/07..10/15                  → 그 쌍의 percentile  0%   ← 매수 신호!
```

여행은 날짜쌍 하나에 묶여 있지 않다. 창 안의 어떤 조합이든 되므로, 판정해야 할 계열은
**날마다 15쌍 중 최저가**(min-envelope)다. 같은 데이터로 envelope을 내면:

```
오늘 15쌍 최저     1,120,100
60일 envelope 최저   863,900   (9일 전엔 953,200)
envelope percentile     86.7%  ← 지금 사면 안 된다
```

쌍 하나짜리 판정은 **하위 0% = 매수**라고 했을 것이다. 틀린 신호다.

### 설계 결정 (실측 3 반영)

**percentile은 15쌍 min-envelope 위에서 낸다.** `insight.read_market()`이
날짜별 최저가 계열을 만들고 마지막 날의 순위를 그 앞 60일 안에서 구한다.

**곡선은 날짜로 키를 잡는다** (인덱스 아님). 쌍마다 곡선 길이가 어긋나면 인덱스 정렬은
조용히 엉뚱한 날을 비교한다. 날짜 키는 빠진 날이 그냥 기여를 안 할 뿐이다.
날짜 라벨은 UTC — 표시하지 않고 정렬에만 쓰므로 Google이 어느 zone으로 찍었는지
추측할 필요가 없다.

동률은 midrank: `(아래 개수 + 0.5 × 동률 개수) / N`. 60일 내내 같은 가격이면
0%가 아니라 50%가 나와야 한다 (가만히 있는 것은 신호가 아니므로).

**알림에 실을 값은 제약 만족 최저가**다 (실제로 살 수 있는 것). envelope은
무제약 계열이므로 둘이 다르면 메시지가 어느 값을 순위 매겼는지 밝힌다.

**Google의 typical_price_range(`payload[5][4][1]`/`[5][5][1]`)는 안 읽는다.**
파싱까지 해 뒀다가 종료 후 리뷰에서 뺐다 — 읽는 곳이 0곳이었고,
"그동안 최저 863,900원"이 같은 질문에 더 잘 답한다.

**저장하지 않는다.** 곡선의 마지막 점은 우리 quote로 이미 재생 가능하고(실측 2),
과거 60점은 매 실행 다시 온다. 매 실행 61점 × 30쌍을 append하면 중복만 쌓인다.

**요청은 늘지 않는다.** 이미 받고 있는 같은 HTML에서 파싱만 추가한다.

## 발견: Google이 60일치 가격 곡선을 준다 (SerpApi `price_insights`)

`CLAUDE.md`에 "Google은 판정만 주고 근거 곡선은 안 준다"고 적었는데,
**SerpApi 응답의 `price_insights`에는 일별 60개 포인트가 들어있다:**

```
lowest_price        1,120,100
price_level         "typical"
typical_price_range [1,050,000, 1,850,000]
price_history       [[unix_ts, price], ...] 60개 (일별)
```

**그런데 SerpApi가 필요 없다. 이 곡선은 우리가 이미 받는 HTML 안에 있다.**

```
payload[5][10][0]   [[unix_ms, price_krw], ...]  62개 포인트 (일별)
payload[5][4][1]    typical_price_range 하한 1,050,000
payload[5][5][1]    typical_price_range 상한 1,850,000
```

가격 배열이 SerpApi `price_history`와 **완전히 일치**한다 (SerpApi는 ms를 s로
바꾸고 앞쪽 중복 1개를 지워 61개로 준다). 즉 파싱만 붙이면 공짜다.

**P-4에 미치는 영향이 크다.** "실제 데이터 30일 누적 전엔 시작 금지"라는
선행 조건이 사라진다. 오늘 당장 62일치 곡선 위에서 percentile을 낼 수 있다.

**단, 확인할 것**: 이 곡선이 *이 날짜쌍*의 가격인지 *노선 일반*의 가격인지
아직 모른다. 날짜쌍을 바꿔가며 곡선이 달라지는지 보면 판별된다.
또 이 곡선은 하루 1점 · 62일이 전부고 제약(경유·소요시간) 필터가 안 걸린
값이다. 우리 자체 히스토리는 실행마다 · 날짜쌍마다 · 여정마다 쌓이므로
해상도가 다르다. 둘은 대체재가 아니라 보완재.

**트리거 대기**: SerpApi 상시 전환. 무료 250회/월로는 상시 수집 불가
(현재 하루 60회). Starter $25/월도 1,000회라 부족. 파서 수정 후 fast-flights가
SerpApi와 동일 결과를 내므로 전환 이유도 사라졌다.

1. **다구간(오픈조)** — fast-flights로는 불가. 필요할 때 무료 티어로 조회

   트리거 대기 — 같은 종류 실패가 한 번 더 나오면 자동화
