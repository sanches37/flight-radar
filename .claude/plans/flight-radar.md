## P-1a — fast-flights 통합권 연결  ✅ 완료

실측으로 확정된 것 (2026-08-21, fast-flights 3.1.0):

- `curr=KRW`로 **가격이 KRW 정수**로 온다. 통화 필드 불필요 → 트리거 대기 항목 유지
- `Quote` 스키마 **변경 없이** 전 필드가 채워진다. P-0 이월 항목(fake 필드 검증) 해소
- `metadata.airlines`가 이름→IATA 매핑을 준다 → `carriers`는 코드로 저장
- 요청당 ~1.3초. 3초 간격 삽입 시 30요청 = 실행당 ~2분 10초. 차단 없었음
- 수집량: 실행당 222건 (date pair 30 × 여정 5~11)

**함정 2개 (재발 방지용으로 테스트에 고정)**

1. **duration을 현지시각 뺄셈으로 구하면 안 된다.** 출·도착 시각은 각 공항 현지시각이라
   ICN→LIS에서 8시간이 조용히 사라진다 (29h15m → 21h15m). 구간 duration 합 + 경유 대기
   (같은 공항이므로 뺄셈 안전)로 계산한다. `google_flights.py:_elapsed_minutes`
2. **fast-flights 3.1.0 파서 버그.** `parser.py:77`이 가격을 무조건 읽어서, Google이
   "가격 미제공"으로 주는 여정(`k[1] == [[], "..."]`)이 하나라도 섞이면 `IndexError`로
   **그 페이지 전체가 날아간다.** 실측에서 icn-lis 15쌍 중 8쌍 손실.
   `_parse`가 파싱 전에 해당 항목을 걸러낸다. upstream이 고치면 이 8줄을 지우고
   `get_flights`로 되돌리면 된다

**종료 후 리뷰**: 발견 2건 → 수용 2 / 기각 0 / 트리거 대기 0.
(`pause_seconds` 생성자 파라미터 = 호출처 0곳 YAGNI → 상수로 환원 /
CLI 키 `"google"` vs 저장값 `"google_flights"` 불일치 → `PROVIDERS`를 `cls.name`에서 파생)

**다음 Step에서 깨질 것**: 로컬에서 되던 스크레이핑이 GitHub Actions IP에서
차단될 수 있음. P-2에서 실패 감시가 필수인 이유.

## P-1b — 분리 발권 조합  (P-2 뒤로 미룸)

**미룬 이유**: 출발까지 45일뿐이고 P-4 percentile 판정이 30일 히스토리를 요구한다.
통합권만이라도 매일 쌓기 시작하는 것이 분리 발권보다 급하다.

1. `인천→허브`와 `허브→목적지`를 따로 조회해 합산 (`Quote.legs` 채움)
2. 자가환승 최소 연결시간 가드 (예: 3시간 미만 조합 제외)
3. **요청량 압축이 핵심.** 순진하게 짜면 실행당 130+요청(≈9분).
   - ICN→허브 / 허브→ICN은 **두 노선(LIS·OPO)이 공유**한다 → 허브당 11요청, 4허브 = 44
   - 목적지 구간은 허브×목적지당 11요청 = 88
   - 실측 출발일 5개 / 귀국일 5개뿐이므로 date pair가 아니라 **날짜 단위로 캐시**하면
     같은 실행 안에서 재사용된다. 이 캐시를 provider에 둘지 tracker에 둘지 P-1b에서 결정
4. 허브 4개가 과한지 실측 후 축소 검토

**다음 Step에서 깨질 것**: 요청량이 3배가 되면 P-2의 Actions 실행 시간·차단 위험도 3배.
